# Form Structure in Source-Tree Extraction

The current extraction path does not run a separate form-inventory model pass or page-map model pass. Form structure is represented in the source tree and projected into compatibility fields where needed.

## Source-tree structure

Parser-provided spans are organized into `DocumentSourceNode` records:

```typescript
type DocumentSourceNodeKind =
  | "document"
  | "page_group"
  | "page"
  | "form"
  | "endorsement"
  | "section"
  | "schedule"
  | "clause"
  | "table"
  | "table_row"
  | "table_cell"
  | "text";
```

The grouping code uses source text, parser titles, form numbers, and page structure to identify declarations, policy forms, endorsements, sections, and schedules. It may reorganize existing nodes, but it must keep every node tied to real source spans.

## Form inventory compatibility

`document.formInventory`, `document.documentMetadata.formInventory`, and `reviewReport.formInventory` are compatibility projections from source-tree form nodes. They are useful for existing UIs, but they are not the canonical source structure. The canonical structure is `result.sourceTree`.

```typescript
interface FormReference {
  formNumber: string;
  editionDate?: string;
  title?: string;
  formType: "coverage" | "endorsement" | "declarations" | "application" | "notice" | "other";
}
```

## Coverage provenance

For v3 source-backed extraction, prefer `operationalProfile.coverages` over legacy flat compatibility rows. Each coverage is a source-backed unit and can contain nested `limits[]` terms:

```typescript
interface OperationalCoverageLine {
  name: string;
  coverageCode?: string;
  limit?: string;
  deductible?: string;
  premium?: string;
  retroactiveDate?: string;
  formNumber?: string;
  sectionRef?: string;
  endorsementNumber?: string;
  limits: OperationalCoverageTerm[];
  sourceNodeIds: string[];
  sourceSpanIds: string[];
}
```

Declaration rows such as `Item 7. Limits of Liability` can preserve nested each-claim, aggregate, retention, deductible, premium, and retroactive-date terms. Endorsement schedules should remain whole endorsement coverage units with adjacent schedule labels paired to their value cells.

Item references remain textual provenance terms. For example, an endorsement value such as `shown in Item 7` is retained as text and does not receive a fabricated numeric `amount: 7`.

## Practical guidance

- Index `result.sourceTree` for document navigation and retrieval.
- Use `sourceSpanIds` and parser bounding boxes for PDF highlights.
- Keep source-heading-derived titles terse.
- Do not maintain a second form-grouping system in the host app when the SDK source tree already groups the document.
- Do not use old page-map extractor assignments to decide whether a section is a coverage, endorsement, condition, or exclusion.
