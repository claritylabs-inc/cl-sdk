In CL SDK 3.2, policy classification is part of the source-backed operational profile, not a separate raw-PDF classifier phase. The operational-profile model receives bounded source evidence from the source tree and returns `policyTypes` alongside the rest of the product-critical facts.

<Callout type="info">
`policyTypes` is the single top-level policy classification field. Do not add a parallel `coverageTypes` alias or a deterministic coverage-origin projection in consumers.
</Callout>

## Operational profile field

```typescript
interface PolicyOperationalProfile {
  documentType: "policy" | "quote";
  policyTypes: string[];
  // policy number, parties, dates, premium, coverages, endorsements...
}
```

`policyTypes` contains all detected lines of business, for example:

```typescript
["general_liability", "commercial_auto"]
```

The compatibility `InsuranceDocument.policyTypes` field is projected from `operationalProfile.policyTypes`.

## How it is inferred

Classification is source-backed. The profile merge layer resolves `policyTypes` from:

- explicit policy type values returned by the operational-profile model
- source-backed coverage names and declaration evidence
- existing compatibility hints when available
- a default of `["other"]` when the source evidence does not support a more specific type

The SDK does not run the removed full-PDF classify/page-map/template flow in the current extraction path.

## Multi-line documents

Many package policies cover multiple lines of business. `policyTypes` can contain more than one value, and `operationalProfile.coverages` should preserve each source-backed coverage unit rather than forcing the document into a single line-specific template.
